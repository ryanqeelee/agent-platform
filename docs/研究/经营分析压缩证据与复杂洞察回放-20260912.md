# 经营分析压缩证据与复杂洞察回放

日期：2026-09-12。分支：`codex/analysis-evidence-quality`，基线：本地 main `839cc651`；已 fetch 并确认 origin/main 是该 main 的祖先。

本次完成分支代码与复杂问题基线回放，不合并、不部署。在线回放使用现有生产版本，不是本分支的新代码。结论：目前能够找到有价值的业务关联，但复杂答案仍有明确事实解释和算术一致性问题，不能仅因回答完整就称为高质量。

## 边界与最小改动

本次只修改服务侧：Platform 原生 Agent 的压缩、工具结果说明、预算提醒与经营分析指引。数据治理契约、源表与 Edge 均不修改。Center 不介入分析、审核答案或决定是否交付；Edge 仍负责授权和精确查询。未新增服务、依赖、数据库、答案拦截器或模型外的重试循环。

压缩原路径：工具 JSON → 单条前 2,000 字符 → LLM 摘要 → 旧消息移除。降级归档只有 500 字符。`fileOps` 只识别模型调用的文件读写，未识别 governed query/schema 工具自动落盘的 `input_file`。因此大结果后部限制和工具自行生成的证据文件路径可能丢失；这不是靠调高轮次上限能解决的。

本次改动：

- 自动查询/目录文件纳入已有 fileOps 保留机制，连续压缩、摘要服务失败仍保留路径。沿用每类 50 个路径的边界；修正已满时保留新路径的逻辑，并提示旧路径可能被省略。
- 大查询结果改为合法、有限长度的 JSON 摘要输入：优先 query ID、执行时间、行数/截断及文件引用，再按预算保留完整限制、列和行等字段。明确 `compaction_partial`，不截半个 JSON，也不宣称摘要是完整证据。
- 摘要与分段摘要记录实体、期间、粒度、单位、分子分母、限制与后续修正；重要结论缺少原值/范围时重读精确文件，文件过期则走现有授权查询。
- 分析指引修正截断字段为实际 `query.truncated`；明确目录 `source.tables` 与单表 `definition`，减少已观察到的反复探测目录结构。
- 针对下述真实回放缺陷，补充行存在/可计算资格分离、账面/实物分离、合计/成员分离、明细对账、成本口径差异、目标来源及逐问题交付要求。

保留的是可重读证据的路径，不是无限历史，也不保证沙箱文件永久存在。没有文件或超过保留上限时，必须重新查询，不能从摘要重建原始行。

## 状态 × 路径验收

| 状态 | 普通摘要输入 | 降级归档 | 连续压缩 |
|---|---|---|---|
| 小查询结果 | 原文保留 | 按既有预算或显式部分证据 | 已落盘路径继承 |
| 大结果、尾部有限制 | query身份/截断优先；整字段预算；partial明确 | 保留可容纳身份或明确重取指引 | 自动查询文件继承 |
| 目录自动落盘 | 原目录摘要 | 已有文件路径保留 | 自动目录文件继承 |
| 没有文件 | 不伪造文件；提示重取 | 提示重取 | 不产生伪文件 |
| 非JSON/失败/其他工具 | 沿用旧文本策略 | 沿用旧文本策略 | 不从这类载荷伪造 governed 文件 |
| 摘要丢细节或服务失败 | 事实摘要可以有损，文件路径不靠 LLM 复述 | fileOps独立追加 | 第二次仍继承路径 |
| 路径列表超过50 | 保留较新的新增路径 | 提示旧路径可能省略 | 不无限膨胀 |

对应测试：`TestGovernedCheckpointPreservesLimitsAfterLargeRows`、`TestGovernedCheckpointDoesNotInventMissingEvidence`、`TestGovernedFilesSurviveLossyAndDegradedCompaction`、`TestGovernedFilesOnlyComeFromToolResults`、`TestFileOpsCapsTrackedPaths`。已通过 `go test -p=2 ./internal/agent/compaction ./internal/agent/tools ./internal/agent`。

## 复杂问题回放方法

只运行两个新会话，覆盖三个问题：真实门店异常一题、固定人工数据两题。人工数据不混入企业源库；数值用独立 Decimal 计算复核，不用另一段模型评价充当事实标准。按算术闭合、证据与结论匹配、范围/缺失处理、行动可验证性逐项检查，不给主观总分。

真实回放保留历史示例中的显式约束（不把上午最后交易当作缺数证明、不把同源视图当独立证据）；人工案例也明确要求分解。因此本次是定向挑战，不是无提示盲测，也不是新旧版本统计对比。

### 1. X017 缺少销售：真实复杂问题

[回放会话](https://agent.ronsson-ai.com/platform/operating-analysis/chat/1e5e24e7-a67d-4a9b-9d7f-a0f0fc96167c)。Request ID `RlS4d3n1YfG4`。服务日志模型 `qwen3.8-flash`，上下文窗口200000；09:35:12 UTC明确 `max_iterations_reached iterations=60 max=60`，随后成功交付答案。UI显示“思考30轮、60次工具、9m43s”，UI轮数不能替代后台迭代计数。该请求日志未见 `context_compacted`，不能把本题错误归因于压缩；压缩风险由独立定向测试验证。

问题：分析近期缺少销售的原因，自选有证据支持的窗口，与可比店和不同业务事件交叉核对，区分经营变化/停业/数据延迟，给出已知事实、未知原因和两项优先核查行动。

有价值的分析：从销售下滑继续查库存、变动流水，定位 `transfer_out`，再匹配对手店单据号、方向、金额与行数；识别到货数据水位限制；提出运营工单与调拨原单两项核查。比仅答“最近没有销售”更有洞察。

质量未通过的具体证据：

1. 开头直接断言“不是数据延迟”“没有产生销售业务”，后文却承认缺少正式关店/改造依据、状态码未经确认。源侧未观察到业务不能直接等同物理零业务；全网/发布层完整性标记不能自动证明每店源端无遗漏。
2. 把相同单据号两侧金额/行数匹配写成“货确实到了 X005”。这证明账面对应，不单独证明实物签收；答案末尾又引用 schema 限制，指出入库审核日期不等同当前 check_date，前后结论强度矛盾。
3. 将56行库存的净成本为负描述为“56行均为负库存”。汇总为负不证明每个成员都为负，答案还报告了正的数量合计。应按SKU明细分别计数。
4. 展示08-27/28/29三天调拨成本 −120595.51、−43178.49、−9591.71，合计应为 **−173365.71**；正文却写 **−171925.13**，差 **1440.58**。完整工具记录证实：第30步是净变动，第53步是出库方向明细，答案混用了两套过滤口径。另一个独立错误发生在第49步：计算脚本未读取查询文件，将第30步08-31原值 −37.06 手抄为 −2769.53，造成2732.47的输入偏差；Decimal本身算对也无法纠正错误输入。
5. 销售水位至09-11，却将09-12纳入13天无销售外推。即使标为量级参考，也应区分已覆盖的缺失窗口和未完整覆盖当日。
6. 初期多次写脚本、试探JSON结构后才进入有效查询，60轮预算被耗尽；增加预算本身不会修复上述结论质量问题。

### 2. 同店与新店、结构变化掩盖组内改善

[人工案例回放](https://agent.ronsson-ai.com/platform/operating-analysis/chat/613e8274-03e2-4e8a-9102-12cab42a5b8b)。两题同一会话，5次工具，2m24s。明确为人工测试数据，仅用给定数据和沙箱计算，不查询企业库。

结果：核心数字及分解通过，能指出结构恶化抵消组内改善，能区分算术分解与因果。交付完整性未通过：用户要求两题分别两项建议，最终只给两题合计两项。回答中的“100万搬到B”也应更精确地表述为总量100万内部A/B份额变化，避免让人理解为转移100万。
